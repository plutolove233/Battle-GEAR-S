# 机斗战甲逻辑一致性审查报告

审查日期：2026-07-15  
审查状态：仅审查并记录，尚未修改业务代码  
判定依据（唯一权威）：

1. `new_logic/各动作的生命周期与时点.txt`
2. `new_logic/机斗战甲规则书.txt`
3. `new_logic/行动牌的效果与逻辑.txt`

## 1. 审查范围与结论

本次只阅读了三份权威文档，以及与其直接对应的 Action Engine、动作定义、行动牌效果、回合、商店、地图标记、装备设置、状态和胜利判定代码。装备牌、机师牌的逐卡效果不在这三份文档中，因此没有用其他资料扩展审查。

当前实现已经搭出了动作、步骤、时点和暂停/恢复的主体结构，但仍存在一批会直接改变对局结果的偏差。最严重的问题集中在：多牌响应、多目标攻击、移动动作嵌套、数值修正、聚能/联合/觉醒、地图标记和回合清理。

问题分为：

- P0：会使权威文档中的核心流程或整张行动牌基本失效。
- P1：规则结果明确错误，或绕过了必须存在的动作/时点。
- P2：能力模型不完整、边界行为不一致或尚未完成。
- 待确认：权威文档本身缺少决定实现所需的信息。

## 2. P0：核心流程与整牌失效

### P0-01 响应窗口只支持选择一张牌，和“任意张、最多一张迎击牌”冲突

文档依据：`行动牌的效果与逻辑.txt`“响应窗口”要求一次可选择任意张可响应牌，但最多只能选择一张迎击牌，之后按优先级执行。

代码现状：

- `scripts/ui/response_panel.gd` 只有单个 `_selected_card_instance_id`，点击新牌会覆盖旧选择。
- `scripts/action_core/TimingEngine.gd:350-358` 虽接受数组并排序，但 `TimingEngine.gd:361-363` 只取 `selected_cards[0]`。
- 同处注释明确写着“非迎击牌暂不处理”。

实际后果：

- 无法同时使用一张迎击牌和若干非迎击响应牌。
- 无法一次使用多张掩护或多张推进。
- 文档规定的优先级队列在 UI 层尚未真正成立。

建议修复：把面板改成多选集合，迎击牌单独做“最多一张”约束；TimingEngine 顺序执行全部选择项，并等待每一项产生的子动作完成后再执行下一项。

### P0-02 掩护的效果监听绑定错对象，实际很可能不生效

文档依据：掩护不是“响应攻击”，但在攻击 A 的“攻击时”继续监听并减少 A 的威力；多张掩护按数量累计 `-5 × X`。

代码现状：

- `GeneratedActionEffects.gd:55` 把 `cover_effect1` 标记为 `bind_to_sub=true`。
- `GeneratedActionEffects.gd:569-583` 将效果定义成监听 `ATTACK_AT`。
- 使用掩护时并没有 DIRECT 效果创建新的 attack 子动作；`use_action_card_action.gd:261-289` 因此找不到可绑定的 attack，最终退回绑定到当前 `use_action_card` 动作。
- 原攻击 A 不会命中这个监听绑定。

实际后果：掩护牌可以被展示在窗口里并被使用，但威力 `-5` 不一定写回原攻击 A；加上 P0-01，多张掩护也无法实现。

建议修复：掩护应明确绑定响应窗口对应的原攻击 `attack_action_id`，但不能调用 `RESPOND_ATTACK`，不能把攻击标记为“被迎击牌响应”。

### P0-03 双连声明双目标，但攻击动作仍是单目标模型

文档依据：双连的攻击动作输入 `可选择的攻击目标数：2`。

代码现状：

- `GeneratedActionEffects.gd:241-244` 只传入 `target_count=2`。
- `attack_action.gd:49-50`、`attack_action.gd:102-137`、命中和伤害步骤全程只使用单个 `target_id`。
- UI 目标选择同样一次只回填一个 `target_id`。

实际后果：双连没有完成两个目标的记录、逐目标命中判断、伤害/损伤计算和结算，核心牌效未实现。

建议修复：攻击 record 使用 `target_ids`；目标选择支持最多 N 个且至少一个；命中、伤害、响应来源和损伤执行需要以目标为单位记录和结算。

### P0-04 单次移动直接调用 MapService，完全绕过基础移动动作

文档依据：单次移动必须先确定最优路径，再对路径中的每个格子逐个执行“基础移动动作”；基础移动具有 `基础移动前/时/后/结算` 四个时点，插入效果或中断时应停止。

代码现状：`single_move_action.gd:60-63` 直接调用 `map_service.move_mech_to_hex()` 完成整段路径，没有创建任何 `basic_move` 子动作。

实际后果：

- 路径上的每格移动不会逐次触发基础移动时点。
- 监听“离开格子”“进入格子”“移动中插入”的效果无法按文档逐格介入。
- 一旦中途效果改变动力、地形或可达性，当前动作不能按文档停止/重算。

建议修复：单次移动只负责选终点和算路径；逐格创建 `basic_move` 子动作，父动作逐个等待，并在每格后复核剩余路径与可执行性。

### P0-05 数值修正动作的减少、回复、多类型和攻击对象均不正确

文档依据：数值修正可同时包含护甲、动力、威力、范围、金币；方式包括增加、减少、回复，其中回复不能超过上限、增加可以超过上限；威力和范围的对象是攻击动作。

代码现状：

- `stat_modify_action.gd:37-78` 只读取单个 `stat_type`。
- 护甲和动力无论 `method` 是增加还是减少，都把正 `value` 当正 `delta`，因此“减少 5”会变成“增加 5”。
- `restore` 对动力仍走 `modify_mech_power`，且默认 `THIS_TURN` 允许超过上限，不符合回复语义。
- 威力/范围仍调用 legacy `GameActions.modify_attack_power/range`；后者只查 `game_state.current_attack_id` 和旧 `game_state.attacks`，而新攻击动作的数据在 `Action.record` 中。

实际后果：通用数值动作无法可靠表达权威文档；任何通过 `EXECUTE_STAT_MODIFY` 修改新攻击威力/范围的牌效都有失效风险。

建议修复：统一正规化 method 的符号；区分 add 与 restore 上限；支持 `stat_types` 数组；攻击类修改直接定位 ActionRegistry 中的目标攻击并写 record。

### P0-06 聚能写入旧状态，新的聚能监听器永远接不上

文档依据：聚能应对具体武器叠层；该武器下一次攻击的攻击前增加 `4 × 层数` 威力，攻击结算或回合结束后清除全部层数。

代码现状：

- `GeneratedActionEffects.gd:460-516` 期待状态类型 `ENERGY_CHARGE`，并为它定义三个新时点监听器。
- `GameActions.gd:1699-1720` 实际添加的是旧状态 `NEXT_ATTACK_POWER_BUFF`，且直接 append 到机甲状态，不通过 `add_status` 注册新监听器。
- 新 `attack_action.gd` 也没有调用旧的 `CONSUME_NEXT_ATTACK_POWER_BUFF`。

实际后果：聚能牌看似成功施加状态，但新攻击不会得到威力加成，叠层显示与攻击/回合清除也不能按新逻辑工作。

建议修复：删除这条旧状态分支，统一创建带 `weapon_id`、`stacks`、`source` 的 `ENERGY_CHARGE` 状态并注册状态监听器。

### P0-07 联合状态把触发者和目标写反，且联合攻击后不移除状态

文档依据：机甲1对其他机甲 Target 施加联合；当 `unite=机甲1` 发动攻击并到攻击结算时，由 Target 决定是否立即使用攻击牌；选择攻击并结算后移除这一条联合状态。

代码现状：

- `GeneratedActionEffects.gd:597-600` 添加 UNITE 状态时没有显式保存 `unite`/`unite_mech_id`。
- `ConditionChecker.gd:379-387` 把状态的 `target_id` 当成 `unite` 攻击者，结果监听的是 Target 自己发动攻击，而非机甲1发动攻击。
- `GeneratedActionEffects.gd:640-648` 的“联合攻击”分支只执行使用攻击牌，没有移除当前联合状态。

实际后果：联合触发时机相反；即便触发并攻击，状态仍可能重复触发到回合结束。

建议修复：状态保存 `target_id`、`unite_mech_id` 和来源；条件比较攻击者与 `unite_mech_id`；仅在 Target 确实选择并完成攻击牌后按 `status_id` 精确移除。

### P0-08 觉醒无法识别中文牌 ID，并用“第一张弃牌”替代玩家选种类

文档依据：先分别查找弃牌堆中的预判、识破；存在时随机取该种一张，不存在时玩家选择弃牌堆中的一种，再取该种一张和牌堆顶一张；最后统一执行获取牌动作。

代码现状：

- `GameActions.gd:2424-2459` 用英文子串 `predict`、`expose` 搜索卡牌 ID，但实际 ID 是 `action_007_预判`、`action_012_识破`。
- 缺少目标牌时，代码注释明确标为 Simplified，直接拿弃牌堆第一张，不弹出按“牌种类”选择的 UI。
- 最后直接改牌堆和手牌，没有执行统一的 `gain_card` 动作和三个获取牌时点。

实际后果：即使弃牌堆中有预判/识破也会被当作不存在；玩家选择规则丢失；获取时点与手牌 AVAILABILITY 注册也可能遗漏。

建议修复：按明确的 card_def_id 匹配；实现两轮“按种类选择”；临时区收集完成后一次执行 gain_card 动作。

### P0-09 陷阱数值、动作入口和损伤决定方都错误

文档依据：陷阱对中心及相邻一格机甲造成 `2 伤害 + 2 损伤`；损伤由受影响机甲方决定，优先设置在部件装备牌上。

代码现状：

- `GameConfig.gd:75-78` 配置为 `3 伤害 + 1 损伤`。
- `MarkerService.gd:98-126` 直接修改 HP 并直接调用 DamageTokenService 自动放置，没有执行生命变动/损伤变动动作。
- 自动放置不能让每个受影响机甲方逐个选择。

实际后果：数值结果、决定方、放置流程和全部相关时点都不符合文档。

建议修复：配置改为 2/2；爆炸对每台机甲依次创建 HP_CHANGE 与 DAMAGE_CHANGE 子动作；损伤执行者设为该受影响机甲方，并应用陷阱专用的部件优先规则。

### P0-10 事件标记使用了不存在的事件槽 ID

文档依据：事件标记翻开一张事件牌并设置到该机甲的事件区域。

代码现状：

- `GameSetupService.gd` 创建的事件槽 ID 是 `event`。
- `MarkerService.gd:70-71` 却检查并写入 `event_1`。
- `EventTimerService.gd:25-29` 同样只读取 `event`。

实际后果：事件牌会被抽出并改 zone，但没有真正进入机甲事件槽，后续计时器也看不到它。

建议修复：统一槽位 ID；设置事件牌时同步初始化计时数、注册新逻辑效果，并处理原事件槽已有牌的替换规则。

## 3. P1：明确规则偏差

### P1-01 有“可用条件”的辅助牌仍可在主阶段主动使用

文档依据：玩家主动使用时只能使用“没有可用条件”的行动牌；迎击/掩护等有条件牌只能在对应窗口使用。

代码现状：

- `app_root.gd:559-565` 只按 `action_type == 迎击` 禁止主动使用。
- 掩护是辅助牌但具有 AVAILABILITY 条件，因此会通过 UI 主动使用检查。
- `use_action_card_action.gd:82-99` 只拒绝“纯 AVAILABILITY 且没有 DIRECT/LISTEN”的牌；迎击与掩护都同时有其他效果，服务层仍可直接调用。

建议修复：是否可主动使用应根据该牌是否定义 availability 条件以及当前触发上下文判定，而不是只看牌类型。

### P1-02 攻击次数在效果执行前消耗，且效果导致的攻击牌使用也会消耗

文档依据：只有玩家主动、非效果使用攻击牌时，才在使用行动牌动作结算后消耗一次回合攻击数。

代码现状：`use_action_card_action.gd:207-213` 在执行 DIRECT 效果前立即 `attack_count_this_turn += 1`，没有区分主动使用与联合等效果使用，也没有等 USE_ACTION_SETTLE。

实际后果：后续动作取消/失败仍可能耗次数；联合等效果允许使用攻击牌时也会错误消耗回合次数。

建议修复：record 明确标记 `is_player_initiated`；仅在成功结算且为主动攻击牌时提交次数消耗。

### P1-03 攻击牌预检查没有计算“所有可能范围修正后的最大范围”

文档依据：攻击牌点击前应预提取所有可能增加范围的效果，计算最大范围；最大范围内无目标时点击无效。

代码现状：`app_root.gd:567-590` 只遍历当前武器的基础范围，并且只在玩家 UI 入口检查；ActionService 直接调用、AI 和其他入口没有同等校验。

建议修复：提供规则层统一的“最大可能攻击范围”查询，纳入可用的范围修正效果；UI 和动作验证共用该查询。

### P1-04 弃置牌后时点发生时，牌仍在临时区而非弃牌堆

文档依据：确定真正弃置牌后发“弃置牌前”；随后将牌转移到对应弃牌堆，再发“弃置牌后”。

代码现状：`discard_card_action.gd:26-31` 的顺序是移入临时区 → 发 DISCARD_AFTER → 再 transfer_to_pile。

实际后果：监听弃置牌后时点的效果观察到的牌区与文档不一致；依赖“已在弃牌堆”的获取/统计效果会错误。

建议修复：保留必要快照，但在 DISCARD_AFTER 发出前完成弃牌堆转移；离场效果应读取快照而不是依赖牌仍在临时区。

### P1-05 攻击动作抢先承担攻击牌/迎击牌弃置，破坏使用行动牌生命周期

文档依据：非虚拟行动牌应在自己的 USE_ACTION_SETTLE 进入行动弃牌堆；攻击动作在 ATTACK_SETTLE 后只清理攻击动作信息。

代码现状：

- `attack_action.gd:332-350` 在攻击 cleanup 中弃置攻击牌和迎击牌。
- `use_action_card_action.gd:315-325` 对反击等牌故意跳过自身结算弃置，交给原攻击 cleanup。

实际后果：牌的区域变化绑定到了攻击动作而不是使用牌动作；取消攻击、无效攻击或监听后续时点时容易产生 temp_zone 残留，代码只能在 TurnService 做兜底清理。

建议修复：临时监听器的生命周期和牌所在区域解耦；所有行动牌统一由 USE_ACTION_SETTLE 弃置，ATTACK_SETTLE 只清攻击 record/监听器。

### P1-06 预判的弃牌执行者错误地改成系统随机

文档依据：预判效果2由机甲1从目标的未知行动牌中选择一张弃置。

代码现状：`ActionService.gd:1146-1159` 对 `from_target` 且未指定执行者的情况强制设为 `system_random`；GeneratedActionEffects 没有传入机甲1作为 executor。

实际后果：预判使用者失去选择权，实际结果是随机弃牌。

建议修复：执行者设为预判使用者；UI 可保持牌面未知，但允许按未知牌位选择。

### P1-07 维修“移除2损伤”不让机甲1逐个选择区域

文档依据：维修的损伤变动执行者是机甲1，因此应弹出损伤变动 UI，由机甲1逐个选择移除位置。

代码现状：`damage_change_action.gd:76-80` 对 decrease 直接调用 `remove_damage_tokens`；只有 increase 分支会请求 UI。维修测试也只验证总数减少，没有验证选择区域。

建议修复：decrease 在 executor 为机甲时也进入逐点选择流程，并动态刷新可移除区域。

### P1-08 推进的迎击触发不会使用/弃置推进牌，可被无限重复利用

文档依据：使用迎击牌时列出持有的所有推进，可选择任意数量“使用”（执行各自效果1）。

代码现状：`GeneratedActionEffects.gd:537-554` 为每张推进分别弹一个二选一；选择后只执行 `动力+5`，没有执行该推进牌的 use_action_card，也没有把牌移出手牌或弃置。

实际后果：同一张推进可在后续每次迎击中反复触发；也没有统一的任意数量选择。

建议修复：共用一个聚合选择窗口，选中的每张推进都执行正式使用牌动作或等价的牌区/时点完整流程。

### P1-09 锁定会在“任何人命中目标”后清除，而非 locker 命中时清除

文档依据：只有 locker 发动攻击、Target 为目标的攻击 A 命中时，才移除此锁定。

代码现状：`GeneratedActionEffects.gd:773-781` 使用 `TARGET_HAS_LOCK_FROM_ANYONE`；`ConditionChecker.gd:369-377` 明确不检查攻击者是否为 locker。

实际后果：第三方攻击命中也会消耗这条锁定。

建议修复：改用并完善 `TARGET_HAS_LOCK_FROM_ATTACKER`，同时按 status_id 精确移除对应 locker 的状态。

### P1-10 回合开始的回复、抽牌和金币没有通过规定动作执行

文档依据：回复动力属于数值修正；抽牌属于获取牌；这些动作应产生自己的前/后/结算时点，并在暂停时阻塞后续回合流程。

代码现状：`TurnService.gd:68-119` 先发 TURN_START，再直接 restore_power、draw_from_deck、append 手牌、gain_gold；没有创建 stat_modify/gain_card 子动作，也没有等待暂停。

实际后果：相关监听器看不到动作生命周期；TURN_START 监听发生在动力回复之前；抽牌/金币效果无法插入并阻塞后续流程。

建议修复：把回合周期本身做成可暂停的系统动作，按顺序执行数值修正和获取牌子动作。

### P1-11 回合结束随机 pop 手牌、并发弃牌，且在 TURN_AFTER_END 前提前清状态

文档依据：玩家应选择超上限行动牌与未设置装备牌进行弃置；每个弃置动作可暂停；回合结束后时点应先允许状态效果监听。

代码现状：

- `TurnService.gd:151-160` 用 `pop_back()` 自动选择牌并连续发起弃置。
- 多个 discard 是独立顶层动作，TurnService 不等待它们完成。
- `TurnService.gd:163-176` 在发 TURN_AFTER_END 前先 `_clean_this_turn_durations()`，可能先删除本应在回合结束后自行结算的状态。

建议修复：用一个或一组有明确父子关系的 discard 动作让玩家选择，并逐个等待；TURN_AFTER_END 的监听完成后再做兜底状态清理。

### P1-12 金币标记错误地把骰点直接当金币

文档依据：1~3 得3金币，4~5 得4金币，6 得6金币。

代码现状：`MarkerService.gd:45-55` 直接 `player.gold += roll`。

实际后果：掷1得1、掷2得2、掷5得5，三种结果错误；同时金币增加绕过数值修正动作。

建议修复：按区间映射 3/4/6，并通过 stat_modify(gold) 执行。

### P1-13 商店刷新费用和牌去向均错误

文档依据：每回合一次，花费2金币；所有商店牌放到各自牌堆底，再补满。

代码现状：

- `GameConfig.gd:51` 费用为3。
- `ShopService.gd:192-221` 把所有商店牌送入弃牌堆，再重新初始化。

实际后果：费用多1；刷新会污染统一装备弃牌堆，且改变后续抽牌顺序与回收类效果的可选池。

建议修复：费用改2；普通/高级牌分别放回对应牌堆底，隐藏牌恢复背面状态后再重新补位。

### P1-14 隐藏高级装备查看后的购买路径和补位不完整

文档依据：隐藏牌可10金币直接购买，或2金币查看后再按普通购买规则支付 `cost×1.5`；商店不足时即时补充。

代码现状：

- `app_root.gd:1683-1693` 查看后仍调用固定10金币的 `buy_hidden_advanced`。
- `ShopService.gd:142-166` 购买后把隐藏槽清空，但没有补一张新的隐藏高级装备。

实际后果：查看后的正常购买价格无法使用；隐藏槽会永久为空直到刷新/重建商店。

建议修复：区分未查看直接购与已查看正常购；购买成功后即时补隐藏高级槽并设为背面。

### P1-15 商店购买直接改金币和手牌，绕过数值修正与获取牌动作

文档依据：商店购买和折扣购买明确要求先执行金币数值修正动作，再执行获取牌动作。

代码现状：`ShopService.gd:75-93`、`ShopService.gd:116-132` 等直接 `player.gold -= price` 并 append 到 equipment_hand。

实际后果：金币和获取牌的动作时点均不会发出，相关效果无法监听、暂停或修改。

建议修复：购买流程改成可暂停的复合动作，先支付 stat_modify，再 gain_card，最后补商店槽和消耗折扣层数。

### P1-16 相邻机甲转移攻击的基础规则未实现

文档依据：相邻的其他机甲被攻击时，可以把攻击转移到自己，但转移后不能响应该攻击。

代码现状：Action Engine、攻击动作和响应窗口中没有找到攻击目标转移选择、target 更新及“不可响应”标记的实现。

实际后果：规则书中的基础防护操作完全不可用。

建议修复：在 ATTACK_AT 响应阶段前或作为高优先级可用条件提供转移选择；更新目标记录并关闭新目标的迎击响应资格。

### P1-17 “每回合一次花2金币抽1行动牌”只有常量，没有操作实现

文档依据：主阶段每回合一次，可花2金币抽1张行动牌。

代码现状：`GameConfig.gd` 有 PAID_DRAW 常量，但在 app、battle 和 service 中没有找到实际入口与 once-per-turn 执行流程。

建议修复：增加 UI 操作与复合动作，先检查/支付金币，再获取一张行动牌，并记录每回合已用。

### P1-18 额外的回合上限 HP 判胜与权威胜利条件冲突

文档依据：“太空战场-01”的胜利条件只有敌方玩家机甲全部毁灭。

代码现状：`VictoryService.gd:54-84` 在配置回合数到达时按 HP 比较判胜负；`GameSetupService.gd:76-77` 默认设置教学回合上限12。

实际后果：机甲均未毁灭时游戏也会提前结束，且平局强制判玩家失败。

建议修复：移除该地图的回合上限胜负；如果未来某战役需要回合限制，应作为该战役明文规则而非全局默认。

### P1-19 设置装备在“设置装备牌时”之前已经参与数值和效果

文档依据：步骤5只是把牌放到区域，明确“先不参与数值提供与耐久损伤计算”；步骤6才正式生效，然后发设置装备牌后时点。

代码现状：`set_equipment_action.gd:107-137` 在 place_equip 步骤就写入 `slot.equipped_card`、注册效果并重算动力；`_step_activate_equip` 是空函数。

实际后果：SET_EQUIP_AT 的监听看到的是已生效装备，与文档相反。

建议修复：增加 staged/pending 状态，SET_EQUIP_AT 时牌可见但不参与派生值和监听；activate 步骤再正式挂槽、注册效果并重算数值。

### P1-20 设置装备不会等待旧装备的弃置动作完成

文档依据：动作或时点暂停时，整体及后续步骤必须暂停；替换旧装备要先完整执行弃置装备牌动作。

代码现状：`set_equipment_action.gd:62-78` 调用 `deck_service.discard_card()` 发起独立顶层动作后，立即清槽并继续下一步，没有把 discard 作为子动作等待。

实际后果：旧装备离场效果若请求输入或产生子动作，新装备仍会并行继续设置，可能产生两个流程重叠。

建议修复：通过 execute_sub_action 创建 discard_card，父 set_equipment 进入 waiting_sub_action，弃置结算后再继续。

### P1-21 补给绕过获取牌动作

文档依据：补给应把行动牌堆顶两张和装备牌堆顶一张作为一次获取牌动作的输入。

代码现状：`GeneratedActionEffects.gd:742-745` 分别执行旧原子动作 `DRAW_ACTION`、`DRAW_EQUIPMENT`，没有 gain_card 的前/后/结算时点，也没有统一记录三张牌与来源对应关系。

建议修复：先从两个牌堆锁定三张牌到临时集合，再执行一次 gain_card 动作。

## 4. P2：能力模型与未完成项

### P2-01 通用动作仍普遍只支持单对象

生命周期文档允许攻击者、来源牌、使用牌、持有者/执行者等为多个对象。当前 use_action_card 使用单 `card_instance_id/mech_id/player_id`，attack 使用单 `attacker_id/target_id/weapon_id`。这不仅是未来扩展问题，双连已经实际依赖多目标能力。

建议先完成“数组为主、单值兼容输入”的 record 规范，再逐步迁移动作。

### P2-02 初始设置流程未实现权威规则书的完整步骤

规则书要求：抽3机师选1并支付、4装备和4次换牌、设置装备并弃未设置牌、初始4行动牌（4号位5张）。`GameSetupService.setup_tutorial_battle()` 当前只创建玩家/机甲/牌堆/地图，没有这些选择与初始手牌流程。

如果教学战役有意跳过，仍应由教学战役的权威配置明文覆盖；当前三份文档没有这一例外。

### P2-03 事件计时仍走 legacy hook，且时点位置与“回合结束后-1”不一致

规则书写明事件计时在回合结束后减1。当前 `TurnService` 在 TURN_END 后、弃牌前调用 EventTimerService；EventTimerService 使用旧 EffectEngine hook，并直接弃事件牌。建议把计时、到期和弃置纳入 TURN_AFTER_END 对应的 Action Engine 流程，并等待其完成。

### P2-04 展示牌动作记录了 known_to，但“查看其他机甲信息时单列已知牌”未见完整 UI 消费

`show_card_action.gd` 会在 persistent 时写 `CardInstance.known_to`，但现有敌方信息 UI 中未找到按照“已知：牌名、区域”聚合展示这些信息的明确实现。建议补一条端到端测试确认展示、换区和弃置后的已知信息行为。

### P2-05 地图事件/陷阱触发不是可暂停的动作链

MarkerService 整体是同步服务调用。事件设置、陷阱多机甲伤害/损伤都可能产生输入与时点暂停，当前服务结构无法等待每个受影响对象结算完成。建议增加 marker_trigger 复合动作或让 basic_move 等待标记子动作完成。

### P2-06 现有测试覆盖“当前实现”，但缺少权威规则断言

现有测试重点覆盖响应恢复、维修可生效、反击链等回归问题，但没有覆盖：双连两目标、多牌响应、逐格基础移动、聚能叠层、联合方向、锁定来源、商店牌堆底、金币映射、事件槽一致性。后续修复时应优先补这些规格测试，避免旧测试把偏差固化。

## 5. 待确认项

### Q-01 推进效果1的数值类型缺失

`行动牌的效果与逻辑.txt`“推进”写作：“类型：；数值：5；修正方式：增加”。当前代码按“动力 +5”实现。需要确认空缺类型确实是“动力”。在得到确认前，本报告不把推进效果1本身判为正确或错误；P1-08 只针对迎击触发时没有使用/弃置推进牌。

### Q-02 陷阱同时影响多台机甲时的选择顺序

文档明确损伤由“该机甲方”决定，但没有写多台机甲同时受爆炸时的玩家选择顺序。建议实现前确认：是否按行动顺序逐台结算，还是按爆炸中心距离/标记触发者决定顺序。

## 6. 建议修复顺序

建议分四批，避免同时改动过多异步链：

1. 动作底座：修复 single_move→basic_move、stat_modify、discard 时点、set_equipment 子动作等待。
2. 攻击与响应：多目标 attack、多牌 response、掩护绑定、攻击次数、锁定、预判、相邻转移。
3. 行动牌状态：聚能、联合、推进、觉醒、补给、维修移除选择。
4. 系统规则：TurnService 动作化、地图标记、事件槽/计时、商店、付费抽牌、胜利条件、初始设置。

每批都应先补权威规格测试，再修改实现；不要依赖 legacy `game_state.attacks/current_attack_id` 为新动作补丁兜底。
